## 기존 항목에 새 패키지 올리기

1. [Chrome 개발자 대시보드](https://chrome.google.com/webstore/devconsole)에서 위 ID의 기존 IG Lead Saver 항목을 엽니다.
2. 패키지(Package) → 새 패키지 업로드(Upload New Package)에서 `IG-Lead-Saver-v1.5.0-webstore.zip`을 올립니다.
3. 인식된 버전이 1.5.0이고 권한·도메인 추가가 없는지 확인합니다. 현재 게시 버전이 1.5.0 이상이면 manifest 버전을 더 높이고 다시 빌드해야 합니다.
4. 변경사항을 설명하고 심사에 제출합니다. 실제 업무 환경 최종 확인이 남아 있으므로 심사 후 자동 게시를 해제해 승인 후 직접 게시하는 방식으로 준비합니다.
5. 실계정 업그레이드 확인을 끝낸 뒤 게시합니다. 기존 설치자는 같은 항목의 업데이트를 받으며 기존 스토어 링크를 계속 사용합니다.

기존 등록 항목의 전체 새 패키지를 올리는 절차입니다. [Chrome 공식 업데이트 안내](https://developer.chrome.com/docs/webstore/update)

## 사용자 안내

`RELEASE_NOTES_KO.txt`를 사용합니다. 안내의 핵심은 “자동 업데이트 + 작업 탭 새로고침 1회”입니다. 기존 연결 설정 재입력은 필요하지 않습니다. 팝업은 구버전 코드가 남은 탭을 감지하면 새로고침을 안내합니다.

Chrome의 업데이트 확인과 적용 시점은 즉시가 아닐 수 있습니다. [업데이트 동작과 수동 확인](https://developer.chrome.com/docs/extensions/develop/concepts/extensions-update-lifecycle)

## 백엔드와 배포 순서

확장 1.5는 기존 list/append 메시지 형식을 유지합니다. Apps Script를 동시에 교체하지 않아도 기존 백엔드 응답을 처리합니다. 다만 **시트 이력 조회가 저장 잠금 뒤에서 기다리지 않게 하는 개선은 백엔드 배포를 수정해야 적용**됩니다.

백엔드까지 함께 반영한다면 기존 URL을 유지해 Code.gs 배포 수정 → 기존 1.4와 호환 확인 → 확장 1.5 게시 순서입니다. `IG-Lead-Saver-v1.5.0-backend.zip`과 `BACKEND_UPDATE.md`를 사용합니다. 팀원 각자가 Apps Script를 다시 배포하는 방식이 아닙니다.

## 게시 전 남은 실제 확인

- 같은 확장 ID의 1.4 → 1.5 업그레이드 뒤 기존 URL·이름·캠페인 유지
- 작업 탭 새로고침 뒤 표시된 팔로워와 배지 비교, 신규 프로필 조회 성공/실패 상태 확인
- 실제 테스트 시트에 1건 저장, 중복 저장, 캠페인 전환
- 운영 규모의 스크롤 및 제한 이후 복구

자동 테스트는 이 전환 로직을 모의 저장소로 검증합니다. 스토어 배포·실제 계정 검증을 대신하지 않습니다.

## 문제 발생 시

게시 전이면 대시보드에서 심사 취소 후 수정 패키지를 다시 제출합니다. 게시 후 심각한 회귀가 확인되면 대시보드의 [공식 롤백 절차](https://developer.chrome.com/docs/webstore/rollback)를 우선 검토합니다. 수정 패키지를 제출할 때는 게시 버전보다 높은 버전 번호를 사용합니다.
